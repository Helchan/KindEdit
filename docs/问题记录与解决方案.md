# 问题记录与解决方案

本文档记录 KindEdit 开发过程中发现的重大问题、重复问题、复杂修复、跨平台问题、性能问题、数据安全问题和构建打包问题。普通小修和无复用价值的一次性问题不记录，避免文档噪音。

## 2026-06-15 PDF 连续滚动翻页后整个窗口变为空白

问题现象：

- 打开大型扫描版 PDF 后第一页可以正常显示。
- 使用鼠标或触控板连续滚动翻页后，KindEdit 窗口内容区整体变为空白，只剩系统标题栏。

触发条件：

- 打开包含大量扫描图像页的 PDF。
- 连续滚动经过多页，使页面反复进入和离开 PDF 渲染窗口。

原因分析：

- PDF 页面离开渲染窗口时，React 会卸载页面 canvas 和 Fabric 标注层，但原实现没有显式调用 `PDFPageProxy.cleanup()`，也没有把 canvas backing store 尺寸归零。
- 扫描页通常包含大图像、mask 和解码后的位图数据；连续翻页会让 PDF.js 页面资源和 canvas 图像内存持续累积，最终可能触发 Tauri WebView 白屏。
- Fabric.js `dispose()` 是异步方法，滚动中页面频繁挂载/卸载时，重复 dispose 可能产生 rejection；原实现未捕获该异步 rejection。
- 诊断版错误面板捕获到 `NotFoundError: The object can not be found here. removeChild`。Fabric.js `Canvas` 初始化时会把传入的 canvas 替换为自己的 wrapper，销毁时又把 wrapper 替换回原 canvas；原实现让 React 直接管理同一个标注 canvas，滚动卸载页面时 Fabric 已经移动了该节点，React 再从原父节点 `removeChild` 就会抛异常并使根视图停止渲染。

解决方案：

- PDF 页面渲染完成后调用 `page.cleanup()`，释放 PDF.js 页面级 operator/image 资源。
- 页面离开渲染窗口或渲染任务尚未开始就被取消时，清空 PDF canvas 和标注 canvas 的 width/height，释放浏览器 canvas backing store。
- Fabric 标注层销毁时统一调用封装后的异步 dispose，并捕获 rejection，避免未处理异常导致 React/Tauri 视图失效。
- PDF 标注层改为 React 只管理宿主 `div`，Fabric 在宿主内部命令式创建和接管 canvas；销毁前先把 Fabric wrapper 从宿主中摘除，再调用 `dispose()`，避免 Fabric DOM 替换影响 React 卸载。
- 增加 React 根级错误边界和全局未捕获错误面板，后续前端异常会显示具体错误而不是整窗空白。

影响范围：

- 影响 PDF 阅读视图的滚动稳定性和内存占用。
- 不改变 PDF 打开、保存、大纲、标注数据结构或页面显示结果。
- 改变 PDF 标注层内部 DOM 所有权模型；用户可见标注工具、坐标和保存格式不变。
- Windows WebView2 下也应受益于同一资源释放逻辑，但当前环境未完成 Windows 实机验证。

验证方式：

- 使用目标 PDF `中国医学大成（一）内经分册.pdf` 打开后连续滚动多页，确认页面不会变成整窗白屏。
- 执行 `npm run build` 和 `cargo check --manifest-path src-tauri/Cargo.toml`。
- 使用 `./build_package.command` 生成 macOS `.app` 和 `.dmg`，并在 macOS 打包产物中实机验证。

## 2026-06-15 扫描版 PDF 页面内容显示为空白且滚动卡顿

问题现象：

- 同一 PDF 在系统预览或其他 PDF 软件中第一页有扫描图像内容，KindEdit 中打开后第一页显示为空白。
- 受影响文件的前几页没有可提取文本，页面内容主要来自扫描图片流。
- 大型扫描版 PDF 可以滚动到其他页，但页面内容仍不显示；继续滚动时交互明显卡顿。

触发条件：

- 打开包含扫描图片页的 PDF，尤其是页面图像使用 JBIG2 等 PDF.js 需要 wasm 解码器处理的编码格式时。

原因分析：

- KindEdit 前端原先只加载了 PDF.js 主脚本和 worker，没有向 PDF.js 提供 `wasmUrl`、`cMapUrl` 和 `standardFontDataUrl` 对应资源。
- PDF.js 在解析扫描页图像流时会尝试加载 JBIG2 wasm 解码器；资源缺失时图像流无法正常解码，页面就可能只渲染空白背景。
- 补齐资源后，前端实际仍使用 `pdfjs-dist` modern runtime/worker。该 bundle 依赖较新的运行时 API；在本地对照中 modern bundle 卡在 `Promise.try`，而 legacy build 能把问题 PDF 第 18 页渲染出非白内容。Tauri macOS WebView 对这类较新 Web API 和 worker 图像路径兼容性弱于普通浏览器，因此继续使用 modern bundle 会导致 PDF 页面仍为空白。
- Tauri macOS WebView 对 PDF.js worker 中的 OffscreenCanvas / ImageDecoder 图像路径兼容性弱于普通浏览器；扫描图像和 mask 绘制失败时，原实现会 `renderPage().catch(() => {})` 静默吞掉异常，用户只能看到空白页。
- 原 PDF 视图会为所有页创建 React 页面节点，并且已进入预加载范围的页面会长期保留 canvas、Fabric 实例和键盘事件监听；686 页扫描 PDF 滚动后会不断累积渲染实例，导致明显卡顿。
- 该问题与 PDF 大纲、书签跳转和文本层无关；对扫描件不能用文本提取结果判断页面是否应该为空白。

解决方案：

- 在 Vite 中新增 PDF.js 资源插件，开发服务器直接从 `node_modules/pdfjs-dist` 提供 `/pdfjs/wasm/`、`/pdfjs/cmaps/` 和 `/pdfjs/standard_fonts/`。
- 前端构建时将上述资源复制到 `dist/pdfjs/`，确保 Tauri 打包产物能离线访问。
- `PdfViewer` 调用 `getDocument` 时显式配置 `wasmUrl`、`cMapUrl`、`cMapPacked`、`standardFontDataUrl` 和 `useWorkerFetch`，让 PDF.js 能加载扫描页所需解码资源。
- `PdfViewer` 的 PDF.js runtime 和 worker 均改为 `pdfjs-dist/legacy/build/*`，避免 Tauri WebView 走 modern bundle 的较新运行时依赖。
- 在 Tauri 默认路径中关闭 PDF.js 的 worker OffscreenCanvas 和 ImageDecoder 支持，改走更稳定的主线程 canvas 绘制兼容路径；页面渲染改用 PDF.js 6 推荐的 `canvas` 参数。
- PDF 页面渲染异常不再静默吞掉，失败时在页面内和状态栏显示具体错误。
- PDF 页面只在当前页附近挂载 canvas 与 Fabric 实例，离开范围后释放渲染层和事件监听，避免大型 PDF 越滚越卡。

影响范围：

- 影响 PDF 页面渲染，特别是扫描版 PDF、JBIG2 图像页、部分字体或 CMap 依赖较强的 PDF。
- 影响 PDF 视图滚动性能和标注层生命周期；远离当前视口的页面会释放 Fabric 实例，重新滚回时再按当前标注状态恢复。
- 不改变 PDF 文件打开、保存、密码处理、大纲编辑或标注数据结构。
- macOS 和 Windows 打包产物都应随前端构建产物携带同一套 PDF.js 资源；Windows 仍需补充实机验证。

验证方式：

- 执行 `npm run build` 后检查 `dist/pdfjs/wasm/jbig2.wasm`、`dist/pdfjs/cmaps/` 和 `dist/pdfjs/standard_fonts/` 是否存在。
- 使用 PDF.js modern build 和 legacy build 分别对问题 PDF 第 18 页进行渲染对照：modern build 在本地对照中触发 `Promise.try is not a function`，legacy build 输出非白图像内容。
- 在 macOS 打包产物中打开扫描版 PDF，确认第 1 页图像内容可见。
- 在 macOS 打包产物中连续滚动大型扫描 PDF，确认不再越滚越卡，且渲染失败时能看到状态栏错误而不是静默白屏。
- 在 Windows 打包产物中打开同类扫描版 PDF，确认 PDF.js 资源路径在安装包内可访问且页面不空白。

## 2026-06-14 PDF 书签跳转和滚轮滚动后预览回到第 1 页

问题现象：

- 点击左侧 PDF 书签后，右侧预览区域短暂抖动，随后仍回到第 1 页。
- 在右侧 PDF 预览区域使用鼠标滚轮滚动时，也无法稳定停留在其他页面，状态栏持续显示或回到 `PDF：1/...`。

触发条件：

- 打开包含多页和目录结构的 PDF。
- 点击左侧任意非第 1 页书签，或在右侧 PDF 页面区域滚动到后续页面。

原因分析：

- 第一层问题是 PDF 页面组件使用 IntersectionObserver 同时承担懒渲染和当前页检测职责。观察器没有把 root 明确限定为右侧 PDF 页面滚动容器，并且使用了较大的 `rootMargin` 进行预加载，导致第 1 页在滚动或重新观察后容易被判定为可见。
- 更深层问题是 `PdfViewer` 的 PDF 加载 effect 依赖了 `onStatusChange`；而 `App.tsx` 传入的是内联状态栏回调，每次状态栏更新都会让父组件重渲染并生成新的回调引用。
- 用户点击书签或滚轮滚动时，PDF 视图会更新状态栏；新的 `onStatusChange` 引用触发 PDF 加载 effect 重跑，加载流程又把当前页重置为第 1 页，因此表现为右侧预览抖动、空白和回弹。

解决方案：

- 将当前页检测从页面 IntersectionObserver 中移出，改为由 `.pdf-pages` 滚动容器的 `scroll` 事件按页面位置计算当前页。
- 使用 `requestAnimationFrame` 合并高频滚动计算，避免滚动过程中高频全局状态更新。
- 页面 IntersectionObserver 只负责懒渲染预加载，并将 root 限定为 PDF 页面滚动容器。
- 书签跳转时直接滚动 `.pdf-pages` 容器并同步当前页状态，不再依赖 `scrollIntoView` 和预加载观察器共同决定目标页。
- 在 `PdfViewer` 内部用 ref 保存 `onStateChange` 和 `onStatusChange`，PDF 加载 effect 不再依赖状态栏回调引用。
- 在 `App.tsx` 中将 PDF 状态栏回调抽为稳定 `useCallback`，避免父组件每次渲染都向 PDF 视图传入新的函数引用。

影响范围：

- 影响 PDF 右侧预览滚动、左侧书签跳转、当前页状态栏显示和新增书签默认目标页。
- 不影响 PDF 文件读写、密码打开、大纲数据结构、标注数据结构或文本类文档行为。
- macOS 和 Windows 共享同一套前端滚动计算逻辑；Windows 仍需补充实机滚动和书签跳转验证。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 进行本地 macOS 打包验证。
- 在 macOS 实际应用中打开多页 PDF，分别点击非第 1 页书签和滚轮滚动到后续页面，确认右侧预览不回弹到第 1 页。

## 2026-06-14 PDF 文件无法通过打开面板选择且拖入窗口无反应

问题现象：

- 点击工具栏“打开”按钮后，在系统文件选择面板中能找到 `.pdf` 文件，但文件处于不可选状态，无法点“打开”。
- 将 PDF 文件拖拽到 KindEdit 编辑器窗口中释放后，应用没有打开 PDF。

触发条件：

- 在 macOS 通过 KindEdit 工具栏“打开”按钮选择 PDF 文件。
- 将普通 PDF 或加密 PDF 文件拖入 KindEdit 主窗口。

原因分析：

- 打开文件对话框使用了 `{ name: 'All Files', extensions: ['*'] }` 过滤器。Tauri Dialog 插件会把过滤器传给系统原生面板，macOS 原生面板并不把 `*` 稳定解释为任意文件扩展名，导致 PDF 仍可能被置灰。
- PDF 打开流程只接入了工具栏文件选择结果，没有监听 Tauri 主窗口的拖放事件，因此拖入窗口不会触发按路径打开。

解决方案：

- 将打开文件过滤器改为明确的 Supported Files、PDF、JSON、XML、Markdown、SQL、Code、Text，移除 `*` 形式的 All Files。
- 抽取统一的 `openFilePath` 流程，工具栏打开和窗口拖入文件都通过该流程分发到 PDF 专用打开命令或文本打开命令。
- 通过 `getCurrentWindow().onDragDropEvent` 监听主窗口文件 drop 事件，按拖入路径顺序逐个打开文件。

影响范围：

- 影响工具栏打开文件对话框的可选文件过滤行为和主窗口拖入文件行为。
- 不影响 PDF 保存、大纲编辑、标注保存、文本文件打开保存或会话恢复的数据结构。
- macOS 和 Windows 均使用 Tauri Dialog 与 DragDrop API；Windows 仍需在对应环境补充实机验证。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 进行本地 macOS 打包验证。
- 在 macOS 实际应用中通过“打开”按钮选择 PDF，并将 PDF 拖入主窗口，确认普通 PDF 和加密 PDF 均进入对应打开流程。

## 2026-06-14 树视图展开控件和连线样式不符合预期

问题现象：

- 树视图展开/折叠控件使用三角形，不符合方框加减号的结构树视觉预期。
- 父子节点层级连线使用实线，不符合点线要求。
- 连接线绘制在当前节点展开控件中心列时，会穿过展开/折叠控件方框。

触发条件：

- 打开 JSON、XML、YAML 等分栏视图文档。
- 查看存在多层父子节点的树视图。
- 展开或折叠有子节点的树节点。

原因分析：

- 树节点展开控件沿用了三角形 SVG，并通过旋转表示展开/折叠状态。
- 层级连线使用普通背景色实线绘制。
- 当前节点连接线定位在当前节点控件中心，而不是父节点层级列，导致线条穿过控件。

解决方案：

- 将展开/折叠控件改为随树视图字体缩放的方框，折叠显示 `+`，展开显示 `-`。
- 将垂直和横向层级连线改为 `repeating-linear-gradient` 点线。
- 将当前节点连接线定位到父节点层级列，横向点线只连接到当前节点方框左边缘，避免穿过方框。

影响范围：

- 影响树视图展开/折叠控件视觉、层级连线绘制和父子关系辨识。
- 不影响节点展开折叠逻辑、节点复制、文件读写、格式化、压缩或会话恢复。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 进行本地 macOS 打包验证。

## 2026-06-14 树视图字体缩放和层级关系显示不完整

问题现象：

- 树视图通过 Ctrl+滚轮调整字体大小时，节点类型图标仍保持固定尺寸，导致图标和文字比例不一致。
- 字体大小提示显示在底部状态栏后不会自动消失。
- 树视图父节点和子节点之间缺少层级连线，复杂 JSON/XML/YAML 结构中父子关系不够直观。

触发条件：

- 打开 JSON、XML、YAML 等分栏视图文档。
- 在树视图中按住 Ctrl 并滚动鼠标滚轮调整字号。
- 浏览多层嵌套节点。

原因分析：

- `TreeNode` 的类型图标、展开箭头和行高使用固定像素值，没有随树视图字体大小计算。
- 字体调整状态栏提示直接写入普通状态消息，没有临时提示清理计时器。
- 树视图扁平化节点数据只保留节点和深度，没有保留祖先是否为末尾节点的信息，无法正确绘制层级延续线和拐角线。

解决方案：

- 根据当前树视图字体大小计算节点图标尺寸、图标文字大小、展开箭头尺寸、行高和虚拟滚动高度。
- 为字体调整提示增加 2 秒自动清理逻辑，连续滚动时重置计时。
- 扁平化树节点时记录 `ancestorLast` 和 `isLast`，在每行内绘制父子层级垂直线和拐角线。

影响范围：

- 影响树视图节点视觉比例、虚拟滚动高度、滚动到高亮节点定位和层级关系显示。
- 影响编辑器字体调整和树视图字体调整的状态栏提示生命周期。
- 不影响文件读写、节点复制、展开折叠数据、格式化、压缩或会话恢复。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 进行本地 macOS 打包验证。

## 2026-06-14 JSON 分栏字体调整未同步设置

问题现象：

- JSON 等分栏文档中，树视图和右侧文本编辑区的字体大小没有完整跟随设置窗口。
- 文本编辑区使用 Monaco 内置 Ctrl+滚轮缩放时，只改变编辑器内部字号，不回写 KindEdit 配置，设置窗口仍显示旧值。
- 树视图没有 Ctrl+滚轮字体调整入口，调整时状态栏也不会实时显示当前字号。

触发条件：

- 打开 JSON、XML、YAML 等分栏视图文档。
- 在树视图或文本编辑区尝试通过 Ctrl+滚轮调整字体大小。
- 打开设置窗口查看“编辑器字体大小”或“树视图字体大小”。

原因分析：

- Monaco `mouseWheelZoom` 属于编辑器内部行为，不会触发应用配置更新。
- 树视图只接收 `fontSize` 展示值，没有向上回传字体调整的交互。
- 设置弹窗、状态栏和编辑区字体调整没有共用同一条配置更新路径。

解决方案：

- 关闭 Monaco 原生滚轮缩放，改为由 KindEdit 在编辑器容器中接管 Ctrl+滚轮。
- 为树视图、Monaco 编辑器和 Markdown 编辑器增加 `onFontSizeChange` 回调。
- 在应用层统一限制字号范围为 8 到 28，更新配置状态、同步设置弹窗、延迟合并保存配置，并在状态栏实时显示当前字号。

影响范围：

## 2026-06-06 树视图与编辑器在非 ASCII 内容后同步定位错位

问题现象：

- 右侧 Monaco 光标移动到 JSON 字符串值 `after this week` 时，左侧树视图高亮到后续 `after a month` 值对应节点。
- 右侧光标移动到 `after a month` 时，左侧树视图高亮到其父级 `expirationIntervals` 节点。

触发条件：

- 文档在目标节点之前包含 emoji、中文或其他非 ASCII 字符。
- JSON 数组内存在多个结构相同、字段名重复的对象，例如多个对象都包含 `label` 和 `time`。

- Rust 后端 `TreeNode.startOffset/endOffset` 使用源码 UTF-8 字节偏移。

- 当目标节点之前出现 emoji 等多字节字符时，UTF-8 字节偏移与 UTF-16 偏移开始累积差值。

- 左侧点击树节点时又把 Rust 字节 offset 直接传给 Monaco `getPositionAt`，导致编辑器跳转到目标前方位置。
- 重复字段名让错位表现为相邻同名节点互相串位，但根因是 offset 单位不一致。

解决方案：

- 在前端接收后端树节点后，统一把整棵树的 `startOffset/endOffset` 从 UTF-8 字节偏移转换为 Monaco 使用的 UTF-16 字符串偏移。
- 打开文件、自动类型检测后构树、编辑内容防抖重建树、手动切换文档类型和标签切换重建树都使用同一转换入口。
- 转换过程先收集树中全部 offset，再按文档内容单趟生成映射，避免对每个节点重复扫描整篇文档。
- 树视图复制原始值、左侧点击跳转和右侧光标反查统一使用转换后的前端 offset。

影响范围：

- 影响 JSON、XML、YAML 等 SplitTree 视图的左右同步定位和树节点复制原始值。
- 不影响文件打开、保存、格式化、压缩、会话恢复或用户数据安全。
- macOS 和 Windows 共用同一套前端 offset 转换逻辑；Windows 仍需在对应环境补充真实交互验证。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 验证官方 macOS 打包入口。

## 2026-06-06 JSON 树视图顺序与编辑器顺序不一致且反向同步失效

问题现象：

- 左侧 JSON 树视图中的对象字段顺序与右侧编辑器源码顺序不一致。
- 开启“同步”后，在右侧编辑器点击对应 JSON 字段或嵌套值时，左侧树视图没有稳定自动高亮并滚动到对应节点。

触发条件：

- 打开或编辑包含多个对象字段、嵌套对象和数组的 JSON 文档。
- 用户在右侧 Monaco 编辑器点击某个 JSON key、value 或嵌套结构位置，并期望左侧树节点反向同步。

原因分析：

- Rust 后端使用 `serde_json::Value` 构建 JSON 树，但 `serde_json` 默认对象映射不保证按源码插入顺序输出，导致树节点按 key 映射顺序生成。
- 构树时 offset 搜索依赖前一个兄弟节点的结束位置递进；当对象字段顺序被重排时，后续节点 offset 可能漂移或找不到真实源码位置。
- 前端树视图在自动展开高亮节点父级后，立即用展开前的扁平节点列表计算滚动位置，深层节点可能已高亮但没有滚动到可见区域。
- Monaco 编辑器挂载时注册的光标监听直接闭包引用当时的回调；当树节点解析完成或同步配置变化后，监听仍可能调用旧回调，导致右侧点击后没有使用当前树节点执行反向同步。
- 当前高亮路径不变时，重复点击编辑器同一 JSON 位置不会改变 `highlightedPath` 字符串，React 不会重新触发树视图展开和滚动逻辑。

解决方案：

- 将 `serde_json` 依赖启用 `preserve_order` 特性，使 JSON 对象构树、格式化和压缩遵循源码键顺序。
- 保持反向同步基于 Monaco offset 查找最内层包含节点，并使用半开区间避免相邻节点边界误命中。
- 将树视图的“展开父节点”和“滚动到高亮节点”拆成两个 React effect，在展开状态生效并重新扁平化后再滚动。
- Monaco 光标位置、offset 同步和右键菜单回调改为通过 ref 读取最新回调；普通鼠标点击结束时主动按当前光标位置再发出一次 offset 同步。
- 反向同步命中节点时递增同步信号，确保同一路径重复点击也会驱动树视图重新展开父节点并滚动到目标节点。
- 增加 JSON 文档模块单元测试，覆盖源码顺序和嵌套节点 offset 范围。

影响范围：

- 影响 JSON 树视图显示顺序、右侧编辑器到左侧树视图的反向同步、JSON 格式化和压缩后的对象键顺序。
- 不影响文件打开、保存、会话恢复或用户数据安全。

## 2026-06-06 标签页拖拽只出现拖拽影子但不真实重排

问题现象：

- 标签拖拽时能看到半透明拖拽效果，但原标签仍留在原位置，无法把后一个标签真正移动到前一个标签前面。

- 在标签栏按住某个标签并拖动到另一个标签附近。

- 被拖拽标签使用受控 `translateX` 按鼠标位置实时移动；标签数组重排后按新基准位置重新计算偏移，保持拖拽对象继续贴合鼠标。
- 关闭按钮阻止 pointerdown 冒泡，避免按住关闭按钮时触发标签拖拽。

影响范围：

- 影响标签栏鼠标拖拽排序、普通标签点击选择和关闭按钮点击。
- 不影响标签内容、脏状态、会话恢复、文件保存或编辑器输入。
