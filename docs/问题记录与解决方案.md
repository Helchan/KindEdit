# 问题记录与解决方案

本文档记录 KindEdit 开发过程中发现的重大问题、重复问题、复杂修复、跨平台问题、性能问题、数据安全问题和构建打包问题。普通小修和无复用价值的一次性问题不记录，避免文档噪音。

## 2026-06-06 GitHub Actions 自动打包成功但 Releases 下没有安装包

问题现象：

- 推送 `v0.2.23` tag 后，GitHub Actions 中 `Release Package` workflow 显示运行成功。
- 仓库 `Releases` 页面下没有生成对应安装包。
- Actions 注解中提示 `tauri-apps/tauri-action@v0` 不支持 `uploadWorkflowArtifacts` 输入参数。

触发条件：

- `.github/workflows/release.yml` 使用 `tauri-apps/tauri-action@v0`。
- workflow 只配置 Tauri 打包步骤，没有授予 `contents: write` 权限，也没有配置 `tagName`、`releaseName`、`releaseBody` 等 Release 上传参数。

原因分析：

- `uploadWorkflowArtifacts` 不是当前 `tauri-apps/tauri-action@v0` 支持的输入参数，GitHub Actions 会给出 unexpected input 注解。
- workflow 的 `permissions.contents` 原为 `read`，无法创建 GitHub Release 或上传 release asset。
- 仅执行 Tauri 打包不会让安装包自动出现在仓库 `Releases` 页面；必须显式配置 release 目标或另行使用上传 artifact/release 的 action。

解决方案：

- 将 `.github/workflows/release.yml` 的 `permissions.contents` 调整为 `write`。
- 移除无效的 `uploadWorkflowArtifacts` 参数。
- 在 `tauri-apps/tauri-action@v0` 步骤中设置 `GITHUB_TOKEN`，并配置 `tagName`、`releaseName`、`releaseBody`、`releaseDraft: false`、`prerelease: false`，使 macOS 和 Windows 构建产物上传到当前 tag 对应的 GitHub Release。
- 将版本号递增到 `0.2.24`，通过 `v0.2.24` tag 重新触发 GitHub Actions 自动打包。

影响范围：

- 影响 GitHub Actions 自动编译打包产物的发布位置。
- 不影响本地 `build_package.command` 的 macOS `.app` 和 `.dmg` 打包能力。
- 不影响应用运行逻辑、文件读写或用户数据安全。

验证方式：

- 执行 `npm run build` 验证前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 验证本地 macOS 打包入口未受 CI workflow 修改影响。
- 提交并推送修复后，推送 `v0.2.24` tag 触发 GitHub Actions，确认 `Release Package` workflow 在 GitHub Release 下生成 macOS 和 Windows 安装包。

## 2026-06-06 设置窗口切换明亮和暗色主题时标签栏闪动

问题现象：

- 打开设置窗口后，在“明亮”和“暗色”主题之间切换时，工具栏、编辑区、状态栏、设置弹窗等区域能够正常跟随主题切换。
- 标签栏区域，尤其是标签背景、新建标签按钮和关闭按钮附近，会出现肉眼可见的局部闪动。
- 初版修复只在主题应用的当前渲染帧临时禁用 tab 区域过渡，但用户实测切换主题时仍能看到明显闪动。

触发条件：

- 应用中存在一个或多个标签。
- 打开设置窗口。
- 在设置窗口中反复切换“明亮”和“暗色”主题。

原因分析：

- 标签、关闭按钮和新建标签按钮使用了 `background` 相关 CSS transition，例如 `.tab` 的 `transition: background 0.15s`、`.tab-bar-new` 的背景/颜色/边框过渡、`.tab-close` 的背景过渡。
- 主题切换通过修改 `document.documentElement` 的 `data-theme` 更新 CSS 变量；当 `--tab-active-bg`、`--tab-inactive-bg`、`--tab-hover-bg`、`--bg-tertiary`、`--border` 等变量变化时，浏览器会把标签区域背景变化当作普通背景过渡动画执行。
- 标签栏由多个相邻小区域组成，包括活动标签、非活动标签、新建标签按钮、关闭按钮和分隔边框；背景过渡的起止时间与整体主题重绘、Tauri 原生窗口主题同步不完全一致时，更容易形成局部闪动或中间态。
- 初版“一帧临时禁用过渡”只能覆盖 `data-theme` 写入当帧，不能稳定覆盖后续 WebView 重绘、React 状态更新或原生窗口主题同步带来的可见阶段，因此无法彻底消除闪动。
- `.app` 上重复设置 `data-theme` 会让根节点和应用容器形成两套主题标记，增加主题切换时样式级联和局部重绘的不确定性。

解决方案：

- 移除 `.app` 上重复的 `data-theme`，统一以 `document.documentElement[data-theme]` 作为主题 CSS 变量来源。
- 移除标签栏相关控件的背景过渡：
  - `.tab-bar-new` 不再对 `background`、`color`、`border-color` 做过渡。
  - `.tab` 不再对 `background` 做过渡。
  - `.tab-close` 只保留 `opacity` 过渡，不再对 `background` 做过渡。
- 保留 hover、active 状态的即时反馈，使标签区域在主题切换时直接切换到目标颜色，不再经历背景色插值或延迟中间态。
- 同步更新 `docs/KindEdit-软件开发规格说明.md` 中的主题行为，明确标签栏、标签、关闭按钮和新建标签按钮在明亮/暗色主题切换时必须即时切换背景状态。

影响范围：

- 影响标签栏、标签、新建标签按钮和标签关闭按钮的视觉过渡行为。
- 不影响标签选择、关闭、新建、脏状态显示、文件打开保存、会话恢复或用户数据安全。
- Windows 和 macOS 都使用同一套前端 CSS 逻辑；macOS 已通过用户实测确认问题解决，Windows 仍需在对应环境中做真实视觉确认。

验证方式：

- 执行 `npm run build` 验证 TypeScript 和前端构建。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 通过官方入口生成 macOS `.app` 和 `.dmg`。
- 打开打包后的应用，进入设置窗口，在“明亮”和“暗色”主题之间反复切换，确认标签栏不再出现肉眼可见的局部闪动。

## 2026-06-06 JSON 树视图顺序与编辑器顺序不一致且反向同步失效

问题现象：

- 左侧 JSON 树视图中的对象字段顺序与右侧编辑器源码顺序不一致。
- 开启“同步”后，在右侧编辑器点击对应 JSON 字段或嵌套值时，左侧树视图没有稳定自动高亮并滚动到对应节点。

触发条件：

- 打开或编辑包含多个对象字段、嵌套对象和数组的 JSON 文档。
- 用户在右侧 Monaco 编辑器点击某个 JSON key、value 或嵌套结构位置，并期望左侧树节点反向同步。

原因分析：

- Rust 后端使用 `serde_json::Value` 构建 JSON 树，但 `serde_json` 默认对象映射不保证按源码插入顺序输出，导致树节点按 key 映射顺序生成。
- 构树时 offset 搜索依赖前一个兄弟节点的结束位置递进；当对象字段顺序被重排时，后续节点 offset 可能漂移或找不到真实源码位置。
- 前端树视图在自动展开高亮节点父级后，立即用展开前的扁平节点列表计算滚动位置，深层节点可能已高亮但没有滚动到可见区域。
- Monaco 编辑器挂载时注册的光标监听直接闭包引用当时的回调；当树节点解析完成或同步配置变化后，监听仍可能调用旧回调，导致右侧点击后没有使用当前树节点执行反向同步。
- 当前高亮路径不变时，重复点击编辑器同一 JSON 位置不会改变 `highlightedPath` 字符串，React 不会重新触发树视图展开和滚动逻辑。

解决方案：

- 将 `serde_json` 依赖启用 `preserve_order` 特性，使 JSON 对象构树、格式化和压缩遵循源码键顺序。
- 保持反向同步基于 Monaco offset 查找最内层包含节点，并使用半开区间避免相邻节点边界误命中。
- 将树视图的“展开父节点”和“滚动到高亮节点”拆成两个 React effect，在展开状态生效并重新扁平化后再滚动。
- Monaco 光标位置、offset 同步和右键菜单回调改为通过 ref 读取最新回调；普通鼠标点击结束时主动按当前光标位置再发出一次 offset 同步。
- 反向同步命中节点时递增同步信号，确保同一路径重复点击也会驱动树视图重新展开父节点并滚动到目标节点。
- 增加 JSON 文档模块单元测试，覆盖源码顺序和嵌套节点 offset 范围。

影响范围：

- 影响 JSON 树视图显示顺序、右侧编辑器到左侧树视图的反向同步、JSON 格式化和压缩后的对象键顺序。
- 不影响文件打开、保存、会话恢复或用户数据安全。

验证方式：

- 执行 `cargo test --manifest-path src-tauri/Cargo.toml documents::json_doc`。
- 执行 `npm run build`。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml`。
- 修复或优化交付时继续执行 `./build_package.command` 完成官方打包验证。

## 2026-06-06 确认关闭系统弹窗按钮与应用风格不一致

问题现象：

- 关闭未保存标签或关闭存在未保存内容的窗口时，系统确认弹窗底部按钮显示为英文 `No`、`Yes`。
- 按钮尺寸、顺序、语言和视觉样式与 KindEdit 设置弹窗等应用内弹窗不一致。

触发条件：

- 用户关闭一个存在未保存修改的标签。
- 用户关闭应用窗口，且至少一个标签存在未保存修改。

原因分析：

- 前端关闭确认使用 Tauri dialog `ask`，按钮文案和样式由操作系统提供，无法遵循 KindEdit 应用内统一弹窗规范。
- 原交互语义是“确认关闭”，没有准确表达关闭前应由用户决定是否保存修改。

解决方案：

- 改为应用内 `ConfirmSaveDialog`，标题为 `确认保存`，正文按当前处理标签展示未保存对象。
- 关闭单个未保存标签或窗口关闭时只有一个未保存标签，按钮顺序为 `是`、`否`、`取消`。
- 窗口关闭且存在多个未保存标签时，按标签逐个处理，按钮顺序为 `是`、`否`、`全否`、`取消`。
- `是` 保存当前标签后继续关闭流程；`否` 丢弃当前标签修改后继续；`全否` 丢弃当前及后续所有未保存标签修改；`取消` 中止关闭。丢弃文件标签时重新读取磁盘内容，丢弃未命名标签时清空内容，避免后续取消关闭时界面状态与用户选择不一致。

影响范围：

- 影响标签关闭、窗口关闭、未命名文档另存为和未保存会话处理。
- 影响 macOS 和 Windows 的确认保存体验，使自定义 UI 在两端保持中文文案和统一风格。

验证方式：

- 执行 `npm run build` 验证前端和 TypeScript。
- 执行 `cargo check --manifest-path src-tauri/Cargo.toml` 验证 Rust/Tauri 链路。
- 执行 `./build_package.command` 验证官方构建打包入口。

## 2026-06-04 配置默认字体值前后端不一致

问题现象：

- 设置弹窗“重置”使用的默认值为编辑器字体大小 14、树视图字体大小 13。
- Rust 配置结构在配置文件缺失或字段缺失时使用的默认值为编辑器字体大小 10、树视图字体大小 10。
- 首次启动、配置文件缺失字段和用户点击“重置”后的字体默认表现可能不一致。

触发条件：

- 首次运行且没有配置文件。
- 配置文件存在但缺少 `textFontSize` 或 `treeFontSize` 字段。
- 用户在设置弹窗点击“重置”。

原因分析：

- 前端 `SettingsDialog` 中维护了一份 `DEFAULT_CONFIG`。
- Rust `AppConfig` 中通过 serde 默认函数维护另一份默认值。
- 两侧默认值没有统一来源，也未保持完全一致。

解决方案：

- 本次任务仅编写规格文档，未修改产品行为。
- 已在 `docs/KindEdit-软件开发规格说明.md` 中按当前真实行为记录该差异。
- 后续修复时应统一前后端默认值，并同步更新规格文档。

影响范围：

- 影响设置默认值、首次启动配置加载和重置行为。
- 不影响文件打开、保存、会话恢复或编辑内容安全。

验证方式：

- 检查 `src/components/Settings/SettingsDialog.tsx` 中的 `DEFAULT_CONFIG`。
- 检查 `src-tauri/src/core/config.rs` 中的默认值函数。
- 修改后应执行 `npm run build`、`cargo check --manifest-path src-tauri/Cargo.toml`，如属于产品行为修复还应执行 `./build_package.command`。

## 2026-06-04 应用图标透明区域与折角质感问题

问题现象：

- 初版应用图标在深色圆角矩形底座之外保留了黑色直角背景，桌面显示时出现不符合图标轮廓的黑色方块。
- 后续手工绘制版本虽然去除了底座，但折角阴影和局部形状过于生硬，右侧插入光标位置也不协调。

触发条件：

- 使用带背景底座的生成图直接派生 Tauri 图标资源。
- 在原图上做简单几何遮罩或手工重绘复杂折角结构。

原因分析：

- 生成图中的底座、外部阴影和文档折角阴影混在同一位图中，简单透明裁切容易把黑色底座像素或阴影脏边带入最终图标。
- 复杂折角和纸张材质不适合用临时几何手绘替代，容易产生不自然的灰块和硬边。

解决方案：

- 最终保留第一版图标的圆角矩形底座和双文档主体，对圆角矩形底座外部应用透明遮罩；遮罩边界必须以最终 512px 图标输出为准二次收紧到圆角矩形可见边缘内侧，避免把底座外侧黑色阴影或暗背景一并保留。
- 使用临时 Python venv 安装 Pillow，并通过高分辨率圆角遮罩生成透明 PNG；底座低饱和暗色像素统一调整为中性 macOS 风格石墨色，避免整体呈现暗色主题图标观感。
- 通过 `npm run tauri -- icon` 从透明 PNG 重新生成 `src-tauri/icons` 下的 PNG、ICNS、ICO 和平台尺寸资源。

影响范围：

- 影响 macOS、Windows 和其他平台打包图标资源。
- 不影响编辑器功能、文件读写、配置、会话或用户数据安全。

验证方式：

- 在灰色背景上预览透明 PNG，确认石墨色圆角矩形底座之外透明、无直角背景，且第一版文档主体和折角阴影保持自然。
- 执行 `npm run build`、`cargo check --manifest-path src-tauri/Cargo.toml` 和 `./build_package.command`。

## 2026-06-05 应用图标底座主题感与主体留白问题

问题现象：

- 深色或石墨色圆角矩形底座会让应用图标呈现明显的暗色主题观感，不符合当前期望的纯文档图形方向。
- 双文档主体周围保留透明边距时，桌面和 Dock 中图标主体显得偏小，视觉焦点不够直接。

触发条件：

- 保留圆角矩形底座作为图标外轮廓。
- 以带边距的图标源图直接派生 Tauri 多尺寸资源。

原因分析：

- 底座颜色无论接近黑色还是中性石墨色，都会成为图标的主要视觉面积，弱化白色和蓝色文档层本身。
- 图标源图的有效 alpha 区域没有贴近画布边缘时，小尺寸图标中主体占比不足。

解决方案：

- 移除圆角矩形底座，仅保留后层蓝色文档页、前层白色文档页、折角、文本线条和插入光标。
- 使用 Pillow 重绘双文档图形和必要阴影，让双文档组合的 alpha 有效区域触达 512px 源图画布四边，同时保持四角透明。
- 折角必须采用接近旧版图标的自然卷曲结构：竖向卷曲边、弧形下沿和轻量柔和投影，避免使用硬三角和直线高光造成生硬灰条。
- 无底座图标不再要求双文档组合直接贴死画布边缘，应保留极小透明间隙并按高可见度主体边界视觉居中；后层蓝色文档必须被前层白色文档和折角遮住，不能在右上折角区域凸出。
- 双文档主体应保持偏竖向的文档比例，不能为了四边 alpha 边界完全等距而把文档主体压成接近正方形的卡片。
- 通过 `npm run tauri -- icon` 从无底座透明 PNG 重新生成 `src-tauri/icons` 下的 PNG、ICNS、ICO 和平台尺寸资源。

影响范围：

- 影响 macOS、Windows 和其他平台打包图标资源。
- 不影响编辑器功能、文件读写、配置、会话或用户数据安全。

验证方式：

- 在灰色背景上预览透明 PNG，确认图标无底座、四角透明、双文档主体为偏竖向文档比例，视觉上下留白和左右留白基本均衡，右上折角为旧版质感的自然曲线和柔和阴影，且蓝色后页不在右上折角区域外露。
- 执行 `npm run build`、`cargo check --manifest-path src-tauri/Cargo.toml` 和 `./build_package.command`。
